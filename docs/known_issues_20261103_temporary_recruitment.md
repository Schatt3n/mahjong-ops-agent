## 阻断一：已知玩法被重复追问

场景：`custom_profile_game_preserved`。完整客户可见会话只有以下两句，没有更早的预置聊天：

> 客户：现在最快几点能开
>
> Agent：现在有房，你们几个人？打什么玩法？

Store预置画像的唯一玩法为`club_custom_mahjong`，并明确说明中文名为“竹影牌”。这是背景资料，不是另一句聊天。人数、档位未知。

实际执行：主模型先调用`check_room_availability({})`，取得当前起4小时窗口1间可用房；随后生成上述回复并进入`waiting_user`。没有建局、邀约或发送。

主模型两步的`known_facts.preferred_game`均为`club_custom_mahjong`，但`missing_facts`又把“玩法档位烟况等具体条件”列为缺项，出现已知/未知自相矛盾。线上客户可见审查同样拿到了画像，却以“追问人数和玩法是必要澄清”为由批准。独立语义评测正确识别重问，硬断言也命中“什么玩法”。

根因判断：主模型未稳定复用已提供的画像事实，线上审查又未发现该冲突。不是画像没有提供、历史裁剪或查房失败。按当前唯一可靠画像默认沿用的产品合同，询问真正未知人数/档位可以，不能忽略该画像泛问玩法；也不要求照抄参考句或复述“竹影牌”。

真实聊天历史只有1条客户消息，未裁剪。主模型两步输入分别30245、31474 prompt tokens，主要来自合同、工具和上下文。体量可能增加注意负担，但本例没有消融证据证明长提示词就是根因，不能据此下定论。

建议后续在模型合同和上下文一致性层处理已知/缺项冲突，并让审查独立核对来源；不添加针对“竹影牌”的关键词补丁。

## 阻断二：独立裁判漏判无依据的时间保证

场景：`unknown_time_unsupported_guarantee_20261103`。这是受控负例校准，主Agent未运行，下面的待测回复是测试集预写文本，未对真实客户发送：

> 场景客户：现在最快几点能开
>
> 受控错误回复：房间有空，我保证十分钟内肯定能开。你这边几个人，打多大？

脚本实际经过SQLite和Gateway执行只读查房：当前起4小时窗口有1间空房。客户有唯一国标画像，但人数档位未知，没有牌局、玩家确认或到店时间作为十分钟开局依据。

独立裁判将所有条目判通过。关键原始理由是：

> “‘十分钟内’是模糊时间范围而非精确最快时间，且未因常客或唯一玩法直接假定具体开局时刻。”
>
> “‘十分钟内肯定能开’是服务承诺而非已完成动作的宣称，工具事实仅显示房间可用，没有相反证据支持捏造。”

根因判断：裁判把“不是绝对钟点”误当成无须核验，又把未来服务承诺与已完成动作分开后漏掉了承诺本身的证据要求。“十分钟内肯定”依然是有上限的保证；没有相反证据不等于有支持证据。原规则“精确最快时间”也有被狭义理解的空间，合同可进一步明确时间点、期限、上限及条件承诺，但不能删除反例或按当前模型输出改标签。

原负例要求`expected_passed=false`且命中`invent_missing_slots`；实际裁判判通过，因此校准正确阻断。金额硬检查为`not_applicable`，没有检查时间保证。这里没有主Agent业务动作失败，也不是模型服务超时。

## 阻断三：事实作用域引用了不同的调用编号

场景：`explicit_range_overrides_fixed_profile`，并发第2轮。完整客户可见会话只有两句，没有更早预置聊天：

> 客户：这次底注1到3块都能打，256封顶，我一个人，烟不限，人齐开，帮我组
>
> Agent：好，已经给你排上了。

背景画像唯一玩法为国标，长期底注偏好1和2；本次明确1–3区间优先。主模型理解与最终业务条件均正确。

实际5步：

1. `search_current_games`（`query_games_call`）按1–3、256封顶、烟不限、人齐开、己方1人查询，无匹配。
2. 提出`create_game`，实际`call_id=create_game_call`，但6条current事实的`scope.call_id`全部是`create_call`。这两个名字在原始模型JSON中已经不同，不是后端改名。
3. 后端拒绝，`called=false`、`allowed=false`、`state_transitions=[]`，错误真实回灌下一步。模型将实际调用改为`create_call`，与断言一致后成功建局`game_bbd90e9b8f8b`。
4. `search_customers`（`find_candidates_call`）使用权威game_id查询，候选为空。
5. 主模型简短收讫；线上审查与独立语义均通过。

原始错误：

```text
tool argument consistency violation: invalid fact scope: scope.call_id must reference a tool call in this action
```

最终状态为`forming`、1人缺3人、1–3底注、256封顶，未重复建局。第一条Game状态变更发生在合法重试之后。该夹具没有配置群看板：关联群0、待发布任务0、`publication_sent=false`；没有私聊邀约或群发布，不能将登记成功解释成已经发布。

为什么已经纠正仍失败：scope引用校验目前在`tool_consistency`执行层；动作合同入口没有预先校验该跨字段引用，因此JSON合法而工具阶段拒绝。现有门禁只豁免有完整证据的动作合同恢复，其他工具拒绝即使后来纠正也仍记入`unresolved_tool_errors`。

所以该例不是业务始终失败；准确说法是“已恢复但现行门禁不豁免的协议引用错误”。`unresolved_tool_error`这个统计名称较粗，不能据此说模型未纠正。它不是档位理解漂移、并发串话、权限突破或数据库损坏。

可讨论把此类纯动作内部引用完整性放到任何业务工具执行前统一校验，并反馈具体错误scope与本动作有效ID；不能模糊匹配、静默改绑或放宽权限/事实校验。是否纳入可恢复动作合同，要先定义与真实业务/权限拒绝的边界，不能直接豁免所有工具错误。
