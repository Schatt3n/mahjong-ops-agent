# 产品构想：个人 Agent 协商日常活动

> 更新日期：2026-10-30。状态：产品构想，作为后续产品实验和设计讨论的依据，不代表下述能力已经实现。当前麻将馆运营 Agent 的实现范围以 [README](../README.md) 为准。

让个人 Agent 代表用户，与商家或其他人的 Agent 协商日常活动，从麻将组局切入。

人只需要表达意愿和边界，Agent 负责询问、匹配、拒绝、邀约和跟进，在需要时再请本人决定。

## 1. 要解决的问题

现在的组局沟通需要人反复参与：

- 老板不知道哪些客户今天有空、愿不愿意来，只能逐个询问。
- 客户即使说过自己的习惯，仍会收到不合适的邀请。
- 客户有临时需求时，又需要主动联系、等待和反复协调。
- 多人之间还存在玩法、时间、同桌偏好和信任问题。

产品希望减少无效打扰，让明确的参与意愿更容易形成一次真实活动。

## 2. 两类 Agent

| 角色 | 代表谁 | 核心职责 |
| --- | --- | --- |
| 个人助理 Agent | 每位客户 | 管理偏好、当前状态和临时意愿；筛选邀请；按授权代为答复 |
| 麻将馆运营 Agent | 麻将馆 | 管理场次和空位；收集组局意向；匹配候选人；邀约并推进成局 |

现有麻将馆运营 Agent 可以继续复用。微信群成为可选渠道：组局前主要通过 Agent 一对一协商，成局后按需建临时群沟通。

这是产品层面的多方代理协作方向；现有运营 Agent 内部的输入分流、摘要、话术生成和内容审查仍是一次性模型任务，不因此变成拥有独立业务目标的 Agent。后续实现仍须遵守 [设计准则](design_principles.md) 中的可信执行与隐私边界。

## 3. 个人助理需要理解三层信息

- **长期偏好**：通常工作日不打，喜欢什么玩法、档位和同桌条件。
- **当前状态**：今天是否有安排、是否希望被打扰。在获得授权后，可以参考相关日程信息。
- **临时意愿**：“我今晚想打麻将”，本次意愿可以覆盖平时的习惯，并有明确有效期。

个人助理掌握这些信息，对外只表达必要结果。例如回复“今天不参加”，无需告诉商家用户的工作或请假情况。

## 4. 典型使用流程

平时，麻将馆 Agent 发来邀请。个人助理根据用户的偏好和授权，自动拒绝不合适的邀约，避免打扰本人。

某天用户说：

> 我今晚想打麻将，八点以后可以，帮我看看有没有合适的局。

个人助理随即：

1. 联系麻将馆 Agent，表达本次组局意向。
2. 开启本次意愿对应的邀约接收窗口。
3. 接收场次信息，筛选玩法、时间和同桌条件。
4. 按授权回复，必要时请用户确认。
5. 将参加结果回传商家，持续跟进变更。
6. 活动结束、用户取消或意愿过期后，结束本次寻找。

整个过程需要明确区分：**有兴趣、可能有空、待确认、已确认参加、已取消。**

## 5. 主动通信与账号关系

每个用户需要稳定的身份，以及与个人 Agent 的关联。个人 Agent 可以主动联系商家，也能接收商家后续发来的邀请。

接收消息和打扰用户是两回事：邀请可以先进入 Agent 收件箱，由助理处理；只有值得本人关注的内容才通知到手机。用户能够控制哪些商家可以联系自己、什么时间接收、哪些事情允许自动答复。

未来，个人助理也可以由豆包等产品承担这一角色；当前产品构想不依赖某个第三方已经开放这些能力。

## 6. 信任、评价与关系画像

通过信用分、场后评价和关系记录改善运营，可以分为三类数据：

| 数据 | 例子 | 用途 |
| --- | --- | --- |
| 履约记录 | 到场、迟到、取消、已核实的逃单 | 判断可靠性，制定接待与惩罚规则 |
| 场次反馈 | 沟通体验、是否遵守约定 | 改善后续匹配 |
| 关系偏好 | 不愿与某人同桌、优先和熟人打 | 尊重个人选择，避开不合适的组合 |

匿名评价、信用分和拉黑机制是候选设计。评价如何核实、单店拉黑与平台封禁的范围、是否永久生效，还需要进一步定义。

“谁不愿意和谁打”属于有方向的私密关系，不必转换成对某个人的全局负面评价。

## 7. 可扩展的产品方向

同一套协作方式可以用于聚餐、球局、共同出行、露营、拼车和排练等多人场景：

> 用户表达目标和限制 → 各方 Agent 协商 → 形成可参与的方案 → 按授权确认 → 跟进活动结果。

首个产品实验可以围绕熟悉的麻将馆和少量客户，验证三个结果：**是否减少无效打扰、是否节省协调时间、是否帮助大家成功组局。** 再据此判断哪些能力适合扩展到其他生活场景。
